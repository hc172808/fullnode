Node Operator Guides

Step-by-step instructions for every GYDS Chain node mode — from a quick-start lite node to a high-performance boost validator.

💱

Buy, Hold, Send & Trade GYDS

A node gives people access to the network; it is not automatically an exchange. This software currently supports wallets, balances, native GYDS transfers, token transfers, and EVM-compatible RPC. It does not yet include fiat checkout, exchange listings, swaps, liquidity pools, or an order book.

Wallet Transfers EVM Compatible Exchange Required to Buy
⚠️ There is no built-in “Buy GYDS” button or trustless trading venue in the current node. Do not send money to an unverified seller. A real launch needs a named exchange/on-ramp, published fees, custody rules, and a support process.
1
How people can use GYDS today
  • Create or import a wallet in the dashboard.
  • Add GYDS Chain to MetaMask or another EVM wallet using chain ID 198282.
  • Receive GYDS from a network participant, or receive tokens from an issuer, by sharing the wallet address—not the private key.
  • Send GYDS through the wallet or standard Ethereum-compatible RPC once the sender has funds and gas.
2
How buying would work after a listing

Once GYDS is legally and operationally listed by a real exchange or approved on-ramp, a buyer would:

  1. Create and verify an account with that provider.
  2. Buy GYDS using the payment methods the provider supports.
  3. Withdraw to a wallet configured for GYDS Chain (chain ID 198282).
  4. Confirm the withdrawal network and address before sending; a wrong network can permanently lose funds.
ℹ️ The exchange must support GYDS Chain withdrawals specifically. An exchange listing on another network is not enough.
3
What is required for decentralized trading

To let users trade without a centralized exchange, the project still needs a reviewed DEX design: a swap or order-book contract, liquidity pools and initial liquidity, price/oracle protections, token and pair metadata, slippage and fee handling, indexing, and a trading UI connected to the wallet.

Before real funds are accepted, those contracts should be independently audited and the project should publish the token supply, mint authority, treasury, liquidity ownership/lock terms, risks, and applicable legal/compliance information.

Full Node

Stores the complete chain history. Runs PoS block production, P2P gossip, and the full JSON-RPC API. The standard choice for node operators who want to participate in the network and serve queries without relying on third parties.

Quick Start

1. Run the setup wizard, then deploy

# 1. Open the setup wizard and choose "Full Node" # It generates a .env file with all your config. # 2. Deploy (builds binary + installs systemd service) sudo bash deploy.sh # 3. Check node status sudo systemctl status gyds-fullnode # 4. Tail logs sudo journalctl -u gyds-fullnode -f
Step-by-Step Guide
1
Provision your server

A full node runs 24/7. Choose a VPS or dedicated server with a reliable internet connection (1 Gbps recommended). Popular providers: Hetzner, DigitalOcean, AWS EC2, Vultr.

  • Ubuntu 22.04 LTS or Debian 12 (recommended OS)
  • At least 2 vCPUs and 4 GB RAM
  • 50 GB SSD minimum — NVMe preferred for faster LevelDB I/O
  • Open ports: 30303/tcp (P2P), 8545/tcp (RPC), 5000/tcp (Dashboard)
2
Configure via the setup wizard

Visit /setup on your node dashboard. Select Full Node mode and complete all 7 steps. The wizard generates a .env file you can save directly to the server.

⚠️ Keep your private key safe. Never commit .env to a public repository.

Key settings for a full node:

GYDS_NODE_MODE=full GYDS_CHAIN_ID=198282 GYDS_P2P_PORT=30303 GYDS_RPC_PORT=8545 GYDS_MAX_PEERS=25 GYDS_BOOTSTRAP_NODES=tcp://bootnode1.gydschain.io:30303 GYDS_DATA_DIR=/var/lib/gyds-fullnode
3
Deploy the node

Run deploy.sh as root. It builds the Go binary, installs it as a systemd service, configures the UFW firewall, and sets up log rotation. Deployment does not install fail2ban.

sudo bash deploy.sh

The script outputs progress for each step. If any step fails, it prints an error and exits — fix the issue and re-run; it is idempotent.

4
Verify the node is syncing
# Check the block height is increasing curl -s http://localhost:8545 \ -X POST -H 'Content-Type: application/json' \ -d '{"jsonrpc":"2.0","method":"eth_blockNumber","params":[],"id":1}' # Tail live logs sudo journalctl -u gyds-fullnode -f --no-pager
ℹ️ A fresh full node replays the genesis and all stored blocks on first start. This takes a few seconds. Subsequent starts are instant.
5
Connect MetaMask or ethers.js

Your node exposes a standard Ethereum-compatible JSON-RPC. Add it to MetaMask as a custom network:

  • Network Name: GYDS Chain
  • RPC URL: http://<your-server-ip>:8545
  • Chain ID: 198282
  • Currency Symbol: GYDS

Or download the pre-filled connection config from your dashboard at /gyds-connection-info.json.

Lite Node

Downloads only block headers — roughly 95% less storage than a full node. Cannot validate full transaction history or serve archive queries. Ideal for wallets, light clients, and low-resource VPS instances that need chain awareness without storing everything.

Header Sync Low Storage No Archive
CPU
1 vCPU
Minimal compute needed
RAM
1 GB+
2 GB recommended
Storage
2–5 GB SSD
Headers only, ~95% smaller
Quick Start

Set mode to lite and point to a bootstrap node

GYDS_NODE_MODE=lite GYDS_BOOTSTRAP_NODES=tcp://bootnode1.gydschain.io:30303 GYDS_DATA_DIR=/var/lib/gyds-litenode
Step-by-Step Guide
1
Choose a lightweight server

A lite node can run on the cheapest VPS tier available — even a $4/month instance is sufficient for most use cases.

  • 1 vCPU, 1 GB RAM minimum
  • 5 GB disk is plenty
  • Only port 8545 (RPC) and 5000 (dashboard) need to be open publicly — P2P is outbound-only
2
Configure via setup wizard

Visit /setup and select ⚡ Lite Node. The wizard adjusts the recommended storage limit and peer settings automatically.

The most important setting: provide at least one Bootstrap Node address. Without it the lite node runs isolated and cannot sync headers from the network.

ℹ️ Lite node data is stored in a separate /lite subdirectory of your data dir, keeping it isolated from any full node data.
3
Deploy and verify
sudo bash deploy.sh # Confirm lite mode in logs sudo journalctl -u gyds-fullnode -f | grep -i lite
⚠️ Limitation: eth_getBalance and other state queries may be inaccurate for accounts not in the light client's local state cache. Use a full node for reliable balance checks.

RPC Node

API-only endpoint. No block production, no P2P gossip. Reads the chain state from an existing data directory and exposes the full JSON-RPC API and dashboard. Use this when you want a dedicated read/query endpoint — e.g. a load-balanced API pool — without the overhead of a full node.

API Only Low CPU No Block Production No P2P
CPU
2+ vCPUs
Scales with RPC traffic
RAM
2 GB+
More RAM = better caching
Storage
Shared with Full Node
Points to existing data dir
Architecture

A common production pattern is to run one full node that produces blocks and syncs the chain, and one or more RPC nodes that read from a shared or replicated data directory:

┌─────────────────────────┐ ┌─────────────────────────┐ │ Full Node │ │ RPC Node (read-only) │ │ GYDS_NODE_MODE=full │──data──▶│ GYDS_NODE_MODE=rpc │ │ Port 8545 (internal) │ dir │ Port 8545 (public) │ │ Port 30303 (P2P) │ │ Port 5000 (dashboard) │ └─────────────────────────┘ └─────────────────────────┘
⚠️ Point GYDS_DATA_DIR to the same directory as your full node only if both processes run on the same host — concurrent LevelDB access from two processes is not supported. For separate hosts, use a read replica or snapshot copy of the data.
Quick Start

Set mode to rpc

GYDS_NODE_MODE=rpc GYDS_DATA_DIR=/var/lib/gyds-fullnode GYDS_RPC_PORT=8545 # No GYDS_BOOTSTRAP_NODES needed — RPC node doesn't connect to peers
Step-by-Step Guide
1
Ensure chain data is available

The RPC node reads from an existing GYDS_DATA_DIR. Either:

  • Run it alongside a full node on the same host (use the same data directory, but ensure LevelDB isn't opened concurrently)
  • Copy a snapshot of the data directory from a synced full node
2
Configure and deploy

Visit /setup, select 🔌 RPC Node. The wizard hides P2P and firewall settings that don't apply. Save the generated .env then run:

sudo bash deploy.sh
3
Load balance across multiple RPC nodes

For production API endpoints, run multiple RPC nodes behind nginx or HAProxy for high availability:

# /etc/nginx/conf.d/gyds-rpc.conf upstream gyds_rpc { server 10.0.0.1:8545; server 10.0.0.2:8545; server 10.0.0.3:8545; } server { listen 80; location / { proxy_pass http://gyds_rpc; } }

Boost Node

High-performance validator node. Identical to a full node but with extended peer limits, aggressive bootstrap connections, and optimised block propagation. Best for validators and infrastructure providers on high-bandwidth servers (1 Gbps+).

Block Production Extended P2P High Bandwidth High Resource
CPU
4+ vCPUs
8+ for heavy validator load
RAM
8 GB+
16 GB recommended
Network
1 Gbps+
Low-latency connection critical
Quick Start

Set mode to boost with higher peer limits

GYDS_NODE_MODE=boost GYDS_MAX_PEERS=100 GYDS_P2P_PORT=30303 GYDS_BOOTSTRAP_NODES=tcp://bootnode1.gydschain.io:30303,tcp://bootnode2.gydschain.io:30303
Step-by-Step Guide
1
Choose a high-performance server

Boost nodes are most effective on bare-metal or high-tier VPS instances with guaranteed CPU and low-latency networking. Recommended specs:

  • 4–8 dedicated vCPUs (not shared/burstable)
  • 16 GB RAM for optimal LevelDB caching
  • NVMe SSD with >500 MB/s sequential write
  • 1 Gbps unmetered or very high-cap bandwidth
2
Configure multiple bootstrap peers

The boost node connects to all configured bootstrap peers simultaneously on startup. Provide as many as possible for the fastest initial sync and best block propagation:

GYDS_BOOTSTRAP_NODES=tcp://node1.gydschain.io:30303,tcp://node2.gydschain.io:30303,tcp://node3.gydschain.io:30303

In the setup wizard, enter one peer per line in the Bootstrap Peers field.

3
Deploy and tune OS settings
sudo bash deploy.sh # Increase file descriptor limits for high peer counts echo "gyds-fullnode soft nofile 65536" | sudo tee -a /etc/security/limits.conf echo "gyds-fullnode hard nofile 65536" | sudo tee -a /etc/security/limits.conf # Optimise TCP for high peer counts echo "net.core.somaxconn=1024" | sudo tee -a /etc/sysctl.conf sudo sysctl -p

Genesis Node

Network bootstrapper and initial validator. Starts the chain from block 0 (or inherits existing chain state) and seeds the network by accepting P2P connections. Other nodes connect to this node as their first bootstrap peer. Run this to start a new GYDS network or to act as the first always-on peer in a private network.

Network Bootstrap Initial Validator Must Be Always-On
Uptime
99.9%+
Other nodes depend on you
Network
Public IP
Static IP strongly recommended
Storage
50 GB+ SSD
Same as full node
Quick Start

Start the genesis node, then share your connection info

GYDS_NODE_MODE=genesis GYDS_P2P_PORT=30303 GYDS_DATA_DIR=/var/lib/gyds-genesis # No GYDS_BOOTSTRAP_NODES — genesis node IS the bootstrap node
Step-by-Step Guide
1
Inspect the genesis block

The genesis block defines the initial chain state — validators, pre-funded accounts, and chain parameters. View it with:

./gyds-fullnode genesis

The genesis hash is deterministic — every node on the same network must produce the same genesis hash, or they cannot connect to each other.

2
Configure and deploy

Visit /setup, select 🌱 Genesis Node. The wizard pre-fills a fresh data directory and hides bootstrap node fields (not needed).

sudo bash deploy.sh
✓ The genesis node prints its P2P address and a link to /gyds-connection-info.json in the startup log. Share this with all nodes that want to join your network.
3
Share connection info with other nodes

Other nodes need your genesis node's address as their GYDS_BOOTSTRAP_NODES value:

# On joining nodes, set this in their .env: GYDS_BOOTSTRAP_NODES=tcp://<your-genesis-node-ip>:30303

You can also download the pre-filled connection config from your genesis node's dashboard at /gyds-connection-info.json.

4
Monitor and maintain

Because all new nodes connect to the genesis node first, its uptime directly affects network health. Set up monitoring and alerting:

# Health check endpoint — returns {"status":"ok","height":N} watch -n 5 curl -s http://localhost:8545/health # Set up a cron health-check email alert echo "*/5 * * * * curl -f http://localhost:8545/health || mail -s 'GYDS genesis node down' admin@example.com" | crontab -

Sync Full Node

Actively pulls the complete chain history from configured bootstrap peers. Behaves like a full node once synced: stores all blocks, serves the full JSON-RPC API, and participates in PoS block production. Requires at least one bootstrap peer to sync from.

RAM
4 GB+
8 GB recommended
Bootstrap
Required
At least 1 peer needed
Quick Start

Set mode to sync and configure bootstrap peers

GYDS_NODE_MODE=sync GYDS_BOOTSTRAP_NODES=tcp://bootnode1.gydschain.io:30303 GYDS_DATA_DIR=/var/lib/gyds-fullnode GYDS_P2P_PORT=30303 GYDS_MAX_PEERS=25
Step-by-Step Guide
1
Obtain bootstrap node addresses

You need the address of at least one existing GYDS node to sync from. Options:

  • Download gyds-connection-info.json from an existing node's dashboard and use the P2P address
  • Use official bootnodes if your network has published them
  • Ask the genesis node operator for their bootstrap address

The P2P address format is: tcp://<ip-or-hostname>:<p2p-port>

2
Configure via setup wizard

Visit /setup, select 🔄 Sync Full Node. Enter your bootstrap peer addresses in the Bootstrap Peers field (one per line). Complete the remaining steps and save your .env.

⚠️ Without bootstrap peers, the sync node starts but logs a warning and cannot pull remote chain data. Add peers and restart.
3
Deploy and monitor sync progress
sudo bash deploy.sh # Watch block height increase as the node syncs watch -n 5 'curl -s http://localhost:8545 \ -X POST -H "Content-Type: application/json" \ -d "{\"jsonrpc\":\"2.0\",\"method\":\"eth_blockNumber\",\"params\":[],\"id\":1}" \ | python3 -c "import sys,json; d=json.load(sys.stdin); print(\"Height:\", int(d[\"result\"],16))"'
ℹ️ Sync speed depends on network latency to bootstrap peers and disk I/O speed. A fresh node with a fast SSD and nearby peers can sync thousands of blocks per minute.
4
After sync — operating as a full node

Once the sync node has caught up to the network's head, it behaves exactly like a full node:

  • Participates in PoS block production
  • Serves the full JSON-RPC API and dashboard
  • Gossips new blocks and transactions via P2P

You can switch the mode to full in .env and restart if you want to be explicit about the role after sync is complete.

Test Node

Fully isolated ephemeral node for local development and testing. Data is wiped on every start for a guaranteed clean chain. Binds to loopback only (127.0.0.1) — never reachable externally, even with a misconfigured firewall. Produces blocks every 5 seconds for rapid feedback. No P2P — completely disconnected from the main network.

Quick Start

Run a test node with a single command

# Using the pre-built binary GYDS_NODE_MODE=testnode GYDS_CHAIN_ID=31337 GYDS_DASHBOARD_PORT=15000 GYDS_RPC_PORT=18545 GYDS_DATA_DIR=./data \ ./bin/gyds-fullnode start # Or directly with go run (from source) GYDS_NODE_MODE=testnode GYDS_CHAIN_ID=31337 GYDS_DASHBOARD_PORT=15000 GYDS_RPC_PORT=18545 GYDS_DATA_DIR=./data \ go run . start # Or using the .env.testnode preset (recommended) set -a && source .env.testnode && set +a && go run . start
Step-by-Step Guide
1
Understand what the test node does

When the node starts in testnode mode it:

  • Wipes <GYDS_DATA_DIR>/test/ on every start — always a fresh chain from block 0
  • Sets block time to 5 seconds regardless of the GYDS_BLOCK_TIME value
  • Disables P2P entirely — no inbound or outbound peer connections
  • Binds the dashboard and RPC server to 127.0.0.1 (loopback) — not accessible from outside the machine
  • Exposes the full JSON-RPC API on the configured GYDS_RPC_PORT
⚠️ Do not use test node in production. The data wipe is automatic and cannot be disabled in this mode.
2
Configure using the .env.testnode preset

The repository includes a ready-to-use testnode environment file at .env.testnode. It sets safe local ports and the correct mode — no editing required for basic use.

# View the preset cat .env.testnode # Source it and start set -a && source .env.testnode && set +a go run . start
ℹ️ You can override any variable by setting it after sourcing the file, e.g. export GYDS_RPC_PORT=9545.
3
Connect MetaMask or ethers.js

Add the test node as a custom network in MetaMask or point your ethers.js / web3.js client at the local RPC endpoint:

// ethers.js v6 const provider = new ethers.JsonRpcProvider('http://127.0.0.1:18545'); const blockNumber = await provider.getBlockNumber(); // Should increase every 5s
  • Network Name: GYDS Test Network
  • RPC URL: http://127.0.0.1:18545
  • Chain ID: 31337 (0x7a69)
  • Currency Symbol: GYDS
4
Send test transactions

Use standard Ethereum JSON-RPC calls against http://127.0.0.1:8545. Transactions are included in the next block (≤ 5 seconds).

# Check block number curl -s http://127.0.0.1:18545 \ -X POST -H 'Content-Type: application/json' \ -d '{"jsonrpc":"2.0","method":"eth_blockNumber","params":[],"id":1}' # Check node health curl -s http://127.0.0.1:18545/health | jq .
5
Use in CI / automated tests

The test node starts in under 3 seconds and produces blocks every 5 seconds, making it ideal for integration test suites.

# Example: start test node in background, wait for RPC, run tests, stop set -a && source .env.testnode && set +a ./bin/gyds-fullnode start & NODE_PID=$! # Wait until the RPC responds until curl -sf http://127.0.0.1:18545/health >/dev/null; do sleep 1; done # Run your test suite npm test # or: go test ./... or: forge test kill $NODE_PID
ℹ️ Because data is wiped on each start, every CI run begins from a clean genesis — no state leakage between runs.
